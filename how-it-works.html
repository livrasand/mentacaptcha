How Menta Works

Overview

Menta uses a hashcash-style proof-of-work challenge to tell humans and bots apart. Instead of asking users to identify images, it requires their browser to solve a computational puzzle.

The puzzle is designed to be trivial for a human clicking once, but expensive for automated scripts trying to solve thousands of challenges. No cookies, no localStorage, no third-party telemetry.

Widget mode: captcha flow

1. Initialize Session

Client POSTs to /init with Origin header.

Server validates browser signals, rate limits (per IP, tenant, global) and bot_shield signals, then creates a signed session tied to the client's IP prefix.

2. Get Challenge

Client POSTs to /challenge with session_id and session_signature.

Server validates the session (existence, expiry, IP match, HMAC signature, minimum solve time), then generates a random salt and target difficulty based on the client's reputation.

3. Solve Challenge

Client finds a nonce where SHA-256(salt + nonce) starts with N zeros.

This requires brute-force computation, typically taking 1-3 seconds on a modern browser.

4. Redeem Token

Client POSTs the solution to /redeem.

Server verifies the proof, validates session and challenge signatures, and issues a single-use signed clearance token (JWT).

5. Verify Token

Client includes the token in form submissions; your backend POSTs it to /verify.

Server validates the signature and expiration, consumes the token (single-use via jti), and returns valid/invalid.

Shield mode: universal protection

Menta Shield (menta-shield.js) protects any page without a widget or domain registration. It runs bot_shield evaluation and, when needed, an invisible proof-of-work.

  • /shield/check — evaluates the request (rate limit, bot signals, JA3/JA4). Returns allow, block (403), or shield (PoW challenge at max difficulty).
  • /shield/redeem — verifies the PoW solution and issues a reusable clearance token (JWT, TTL configurable).
  • /shield/verify — server-to-server validation of a clearance token without consuming it; optional IP binding.

The interstitial page (/challenge-page, /verify GET) forces a manual PoW and redirects to the original destination.

Validation Checks

Menta runs multiple validation checks across the challenge lifecycle:

  1. Rate limit per IP / tenant / global. Prevents brute-force from a single address or tenant.
  2. Bot signal checks. Flags automated traffic patterns and known bad user agents.
  3. Browser signals. Validates Origin and basic browser characteristics without fingerprinting.
  4. Session validity. Verifies session exists, hasn't expired, and matches IP prefix.
  5. Session signature. HMAC proves session originated from this server.
  6. Challenge signature. HMAC proves challenge originated from this server.
  7. Nonce entropy. Ensures nonce isn't precomputed or reused.
  8. Proof-of-work. Hash must meet target difficulty.
  9. Client pattern. Solve time analyzed against human range.
  10. Token single-use. Redeemed tokens are consumed on /verify via jti.

Adaptive Difficulty

Menta automatically adjusts difficulty based on client behavior:

  • New IPs get higher difficulty until they establish reputation
  • Fast solves trigger difficulty increase (possible bot)
  • Many failures significantly increase difficulty
  • Consistent patterns may indicate automation

Privacy by design

  • No cookies, no localStorage. Widget and shield hold state in memory only.
  • IP anonymization. By default only the /24 (IPv4) or /64 (IPv6) prefix is used; full IP only if LOG_IP_FULL is enabled.
  • Data retention. Expired challenges, sessions and tokens are cleaned automatically (DATA_RETENTION_HOURS, default 24h).
  • Encryption. SQLCipher at rest + TLS in transit.
  • Rights. /admin/export-data and /admin/delete-data for data subject requests.
